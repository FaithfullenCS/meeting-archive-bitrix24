# Устройство приложения

Состояние `bitrix=short_call` хранится в существующем строковом поле SQLite и в `meeting.json`. Общая функция `followup_state` определяет завершённые звонки с корректной длительностью 0 < durationSeconds < 60 без готовой транскрипции. Также учитывается единственная запись типа record с корректной duration < 60 при пустых outcomes: время соединения может быть больше времени записи. Длительность записи сохраняется как recordingDurationSeconds; размер файла не используется. Сохранённый текст и готовность из outcomes имеют приоритет; состояние не является подтверждённой API-причиной отказа.

С версии 0.2.25 каталог дополняется структурированными CALL_ID из служебных сообщений доступных диалогов. im.recent.list обнаруживает также чаты, отсутствующие в Follow-up; известные чаты сохраняются как кандидаты. Перед добавлением call.followup.get запрашивает только метаданные, проверяются callId/chatId/UUID и участие пользователя. Сырые сообщения, вложения, ссылки на файлы и текст не сохраняются. Курсоры относятся к порталу и пользователю; один проход обрабатывает до 20 диалогов, последнюю страницу и по одной странице догрузки новых/исторических сообщений. Старые страницы списка диалогов продолжаются через OFFSET. Ошибки дополнительного источника сохраняются в служебном state, не удаляют встречи и не блокируют обычный Follow-up. История обнаруживается постепенно; схема SQLite и интерфейс не изменены.

Такое состояние завершает ожидание текста, но не ожидание запрошенного аудио. При старте пересчитываются ранее известные звонки текущего портала и участника, завершаются только удовлетворённые задачи fetch. Скачивание, локальная обработка, импорт и повторная ручная проверка используют прежние API и настройки. Изменение схемы SQLite и новые права не требуются.

Базовый процесс Python/FastAPI запускает локальный интерфейс, каталог Bitrix24, сохраняемую SQLite-очередь и значок pystray. Все HTML/JS/CSS поставляются локально. Сервер слушает `127.0.0.1:8765`; изменяющие запросы требуют защитный токен и проверку источника. OAuth callback допускается только с ожидаемым одноразовым `state`.

Архив и служебное состояние разделены. `meeting.json` содержит перечень файлов и SHA-256; скачивание/копирование выполняется во временный файл, после проверки — атомарная замена. Идентичность Bitrix24 связывает портал, `callId` и UUID сессии, если доступен. Название не участвует в ключе.

Необязательный модуль устанавливается через закреплённый uv в `%LOCALAPPDATA%\MeetingArchive\module`. Базовая сборка и управляемый модуль используют Python 3.12.15. Python runtime, virtualenv, кэш установщика и модели располагаются внутри принадлежащей приложению папки. Удаление разрешено только после проверки точного пути, маркера владения и отсутствия внешних ссылок/junction. Базовая сборка не импортирует torch и модели.

Worker запускается отдельным Python. На stdin передаётся одно JSON-задание; stdout содержит строки JSON `progress`, `result`, `error`. Обычный вывод библиотек направляется на stderr. Отмена завершает дочерний процесс; результаты каждого запуска сохраняются отдельно. GPU-профиль использует torch/torchaudio 2.7.1+cu128, CPU — 2.7.1+cpu. Lock-файлы закрепляют все транзитивные версии и SHA-256.

Внешний адаптер указывает на папку существующего приложения с `src` и `.venv-gpu-ready`. Worker запускает его Python с `-B`, читает исходные модули и пишет только собственные выходные файлы. Исходная программа, её конфигурация и окружение не обновляются. Этот адаптер зависит от совместимости исходных интерфейсов и проверяется отдельно.

Секреты находятся в Windows DPAPI. Настройки и архив не включают OAuth-токены, client secret, Hugging Face-токен или webhook. Журналы и ошибки редактируются перед показом. Локальный архив остаётся приватным: публикация репозитория приложения не должна включать записи и тексты.


## Обновления и локальные уведомления

UpdateManager проверяет только стабильные GitHub Releases репозитория FaithfullenCS/meeting-archive-bitrix24. HTTPS ZIP и checksum сверяются до распаковки; манифест содержит версию и SHA-256 каждого программного файла. Запросы установки, проверки и скачивания защищены существующей сессией и CSRF. Перед установкой останавливается выбор новых задач. Изолированный PowerShell-помощник ждёт завершения процесса, копирует только файлы манифеста, сохраняет предыдущую программу и проверяет запуск через runtime.json и локальный HTTP. Программный откат не откатывает пользовательскую базу, поэтому необратимые миграции не допускаются в этом механизме без отдельного проекта совместимости.

Notifications использует Python/WinRT и системные toast-уведомления с protocol activation. Внешний протокол содержит только разрешённый маршрут и числовые ID. Повторный запуск передаёт маршрут работающему экземпляру через отдельный endpoint с launch capability; запросы из браузерного Origin отвергаются. Интерфейс получает переход при опросе bootstrap и подтверждает его отдельным CSRF-защищённым запросом. Протокол не передаёт launch capability, секреты или команды. Сбой уведомления не меняет состояние завершённой задачи.
